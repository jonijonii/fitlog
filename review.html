구조적 약점

가장 시급

views.js가 1,352줄

오늘·주간·인바디·설정 4개 탭과 30개 함수가 한 파일에. 가장 긴 함수 셋이 100줄을 넘는다 (profileCard 122, supplementEditRow 115, settings 112).

전역 재렌더

상태가 바뀌면 화면을 통째로 다시 그린다. 단순해서 좋았지만 스크롤 튐·포커스 손실·날짜 미갱신 버그가 전부 여기서 나왔다. 지금은 규칙 넷으로 막고 있는데, 규칙을 기억해야만 안전한 구조다.

로드 순서가 곧 의존 그래프

모듈 시스템이 없어 index.html의 <script> 순서가 계약이다. 파일을 추가할 때 순서를 틀리면 조용히 깨진다.

칩 그룹 로직이 4개 파일에 중복

onboarding.js, sheet.js, ui.js, views.js. ui.goalChips로 일부만 통합했고 나머지는 각자 구현.

tests.js가 단일 함수 1,417줄

runTests() 하나에 395건. 어디가 깨졌는지 찾기 어렵고, 일부만 돌릴 수 없다. 브라우저 콘솔에서도 돌아야 한다는 제약이 있어 쪼개기가 간단치 않다.

버그 회고

발생 순서가 아니라 실패의 종류로 묶었다. 같은 종류가 반복됐다.

침묵 실패

에러도 안 나고 아무 표시도 없이 안 되는 것. 사용자에겐 “버튼이 안 눌린다”로만 보인다.

온보딩 ‘시작하기’가 안 눌림

store.todayKey()가 padStart(ES2017)를 썼다. 구형 브라우저에서 그 줄만 죽는데, 요약 화면은 그 함수를 안 거쳐서 멀쩡히 떴다.

ES5 정적 검사를 테스트에 넣어 src/js 전체를 훑게 함

서비스워커가 앱을 통째로 막음

cache.addAll은 전부-아니면-전무다. 파일 하나만 실패해도 통째로 거부되어 캐시가 텅 빈 채로 워커가 켜졌고, 그 상태에서 페이지 요청에 빈 504를 주자 사파리가 “인터넷에 연결되어 있지 않습니다”로 막았다. 앱이 안 열리니 새 워커를 받을 기회도 없어 빠져나올 수 없었다.

cache.add를 하나씩 / 페이지엔 빈 응답 금지 / 자가 복구 화면 + ?nosw 탈출구

표시가 거짓말

데이터와 계산은 맞는데 화면이 다른 것을 보여준다. 데이터가 틀린 것보다 나쁘다 — 앱을 못 믿게 된다.

온보딩이 안 닫힘

.onboarding { display: flex }가 브라우저 기본 [hidden]{display:none}을 이겼다. JS는 정상이라 에러도 안 났고, jsdom은 우선순위를 다르게 계산해서 스모크 105건이 전부 통과했다.

전역 [hidden]{display:none !important} + CSS 소스 직접 검사

보충제 함량 표시가 실제 값과 다름

체크리스트가 preset.amount(고정 라벨)를 보여줬다. 사용자가 함량을 고쳐도 화면은 그대로.

화면 값은 저장된 데이터에서만 뽑기

환경 차이

내 쪽에서는 재현되지 않는 것. 폰에서 도는 앱을 폰 없이 만들었다.

자정을 넘겨도 어제 화면

홈 화면 앱은 껐다 켜지 않으면 계속 살아 있는데, 날짜가 바뀌어도 다시 그리는 코드가 없었다.

visibilitychange/focus/pageshow에서 날짜 비교 후 재렌더

판정 로직 두 곳이 뒤섞임

지방 256%가 적정으로, 마그네슘 87%가 부족으로 나왔다. 매크로와 미량영양소는 ‘과다’의 기준이 다르고(110% vs 상한량), 부족 판정과 상한 판정은 서로 다른 값을 봐야 하는데 하나로 처리했다. 테스트를 통과한 채로 있었고, 리포트를 눈으로 읽다가 찾았다.

이 장치들이 못 잡는 것

  • 실제 iOS/안드로이드 동작 — 공유 시트, 홈 화면 설치, 저장소 정리 정책
  • 보기 좋은지, 쓰기 편한지
  • 영양소 값의 정확성 (전부 추정치)
  • jsdom과 실제 브라우저가 다르게 동작하는 부분

테스트 작성 시 함정 셋 — 실제로 다 겪음

  • jsdom을 믿지 말 것. CSS 우선순위를 실제와 다르게 계산한다
  • 함수를 갈아끼우지 말고 환경을 바꿀 것. todayKey만 스텁하면 내부 호출은 여전히 진짜 날짜를 본다
  • 갈아끼울 자리가 필요하면 내보낸 객체를 거치게 할 것

새 세션에 물어볼 것

  1. views.js 1,352줄을 어떻게 쪼갤까? 탭별 파일이 맞나, 다른 축이 나은가?
  2. 역방향 의존 3개를 풀 가치가 있나? 특히 store → calc. 이 규모에선 과한가?
  3. 전역 재렌더를 유지할까? 규칙 넷으로 막고 있는데 구조를 바꾸는 게 나은가?
  4. 모듈 시스템 없이 로드 순서에 의존하는 게 언제 문제가 되나? 지금 막을 방법이 있나?
  5. tests.js 1,417줄 단일 함수를 어떻게 나눌까? 브라우저에서도 돌아야 한다.
  6. 비개발자용 앱에서 서비스워커가 값어치를 하나? 이번에 앱을 통째로 막았는데 오프라인을 포기하는 게 나은가?
  7. 놓치고 있는 실패 유형이 또 있나? 침묵 실패 / 표시 거짓말 / 환경 차이 — 이 셋 말고.

먼저 실패 유형을 정하고 방어를 깐다

ES5 검사도, CSS 검사도, 배포 검사도 전부 사고가 난 뒤에 만들었다. 폰에서 도는 앱을 폰 없이 만든다는 걸 처음부터 전제했다면 순서가 반대였을 것이다.

가드는 일부러 깨뜨려 확인한다

아무것도 안 잡는 가드를 통과했다고 착각하기 쉽다. 아이콘을 지우고, 캐시 버전을 어긋내고, CSS 규칙을 빼서 실제로 실패하는지 봤다.

테스트 통과와 정상 동작은 다르다

판정 로직 버그 둘은 테스트를 통과한 채로 있었고 출력을 눈으로 읽다가 찾았다. 결과물을 사람이 읽어보는 단계가 자동 검증만큼 중요했다.
